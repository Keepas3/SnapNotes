# Pre-deployment review

Scope: the whole project (`backend/`, `mobile/`, deployment and build config). Each finding has a suggested fix; items marked **FIXED** have been fixed and verified (what changed and how is noted under each). Findings marked **confirmed** were reproduced with an experiment; the experiment is described so it can be repeated.

**Status:** items 2 to 10 are fixed. Item 1 is something you do (run the live spike). The lower-priority list is still open. Nothing in the Docker, Fly or EAS configuration has been built or run (no Docker was available here), and the real Claude API has never been called; see item 9 for exactly what the image changes were checked with.

Severity reflects a single-owner deployment: the internet can reach the server, but only the holder of the access token can use it.

## Fix before deploying

### 1. The Claude integration has never run against the real API (risk, not a defect)
Everything that calls Claude was tested with fakes. I ran the real SDK through the whole pipeline against a mock HTTP transport and checked the requests it would send: correct beta header (`server-side-fallback-2026-07-01`), `fallbacks: "default"`, effort merged with the JSON-schema output format, no `temperature`/`top_p`/`top_k`, the `web_search_20260209` tool, and prompt-cache breakpoints on the notes. Whether the live API accepts all of it (and how real web search citations and `pause_turn` behave) is unknown until it is run.
**Do:** run `backend/spike.py` on two or three real documents first (a PDF, a slide deck, a photo), read the cards and the cost lines it prints, and start with a low `SNAPNOTES_MAX_JOB_COST_USD` (for example 0.50). The spike enforces that limit between stages, like the server (it did not until a later change: the setting was only applied by the server's job worker; covered by `tests/test_spike.py` now). The limit is checked before each stage and leaves out web search fees, so also set a spending limit in the Anthropic Console.

### 2. Link injection in Anki exports (confirmed) — FIXED
`backend/app/export/anki.py` built the Source field's link with `html_text()`, which does not escape double quotes, and `safe_http_url()` only checked the scheme and host, so a web-source URL such as `https://example.com/x"onmouseover="alert(1)` produced `<a href="https://example.com/x"onmouseover="alert(1)">`. URLs come from web search results; a hostile page could therefore plant attributes (and, in Anki's web view, script) in an exported deck.
**Fixed:** `safe_http_url()` now percent-encodes everything that is not valid in a URL (quotes, angle brackets, spaces, backticks, control characters), and the link goes through a new `html_attr()` that escapes quotes. Verified with an HTML parser over eight hostile URLs (quote, single quote, tag break-out, space, newline, backtick, escaped quote, `</a><img onerror>`): every export contains exactly one `<a>` with exactly one `href` attribute. The original reproduction now prints `.../x%22onmouseover=%22alert(...)`.

### 3. The spend ceiling silently turns off for models missing from the price table (confirmed) — FIXED
`PRICING` in `backend/app/llm/client.py` lists only `claude-opus-5-5`, `claude-sonnet-5-5` and `claude-haiku-5-5`. For any other model id (for example `SNAPNOTES_GENERATE_MODEL=claude-sonnet-5`), the cost was `None`, the total was `None`, and the worker's `total_cost or 0.0` made every check pass: the per-document ceiling never tripped and the recorded cost stayed 0. Web search request fees are also not counted (documented, still true).
**Fixed, in three layers:** (1) the server refuses to start when any stage's model has no price, and the error tells you the exact `SNAPNOTES_EXTRA_PRICES` setting to add; (2) that new setting (`{"model-id": [input, output]}` in dollars per million tokens) lets you price a newer model without a code change; (3) at run time a job whose cost cannot be estimated is stopped (`check_cost_ceiling`) instead of being waved through. While fixing it I also found that the four stages read their model from a global settings object while the price table came from the app's own settings; every stage now uses the client's own settings, so "the model that is priced" and "the model that is used" cannot differ. Covered by 23 new tests (price lookup, the environment setting, the ceiling at, under and over the limit, the startup refusal and the stage wiring).

### 4. A 512 MB machine can run out of memory on large PDFs (confirmed) — FIXED
Preparing one 30 MB PDF peaks at about 147 MB of Python heap (the base64 copy plus the request body); the idle server is about 119 MB; the worker ran two jobs at once. Two maximum-size uploads at the same time is roughly 410 MB before the OS and the HTTP client's own buffers.
**Fixed:** `fly.toml` now asks for 1 GB; the worker handles one document at a time by default (`SNAPNOTES_JOB_CONCURRENCY=1`, further uploads queue; a test with two simultaneous uploads confirms the peak is 1); and the upload cap is adjustable (`SNAPNOTES_MAX_UPLOAD_MB`) for anyone running a smaller machine. `DEPLOY.md` explains the numbers. Not changed: the ~5x memory multiplier itself (sending a large PDF inline three times, once per stage). Uploading it once through Claude's Files API would remove both the memory and the repeated bandwidth, but that is an API path I could not test without a key, so it is left as a later optimisation.

### 5. Phone and server can drift apart for good after a restore or a rebuilt volume (confirmed) — FIXED
The phone remembers a sync cursor. If the server's data goes backwards (a volume snapshot restore, which `DEPLOY.md` recommends for backups, or a recreated volume), `pull(cursor=500)` on the rolled-back server returned `cursor: 0` with no signal. The phone dropped its cursor and re-pulled, but nothing told it to delete cards that no longer existed on the server: they stayed studyable, and their reviews were rejected as `unknown_card` and then marked as uploaded, so that study effort was silently lost.
**Fixed:** every database now has a random `epoch` created with it (schema version 3; existing databases upgrade in place). The phone sends the epoch it last saw; the server answers `reset: true` and a full download when the epoch differs or the phone's cursor is ahead of anything the database has numbered. On a reset the phone replaces its cached decks and cards (phantom cards disappear), keeps its review history, and uploads all of it again, so progress the server lost is restored and reviews of cards that no longer exist are rejected cleanly. A restored snapshot keeps its old epoch, so there is an operator command for that case: `python -m app.admin rotate-epoch` (documented in `DEPLOY.md`, "Restoring a backup").
**Verified live in the browser preview:** I upgraded a real version-2 database in place; synced a phone and studied cards on it; deleted the server's entire data folder and restarted it (a rebuilt volume) with one new deck; the next sync dropped both old decks, showed the new one, and left nothing waiting to upload, and the server's three rejected reviews were not stored. Then ran `rotate-epoch` against the live database: the next sync came back `reset: true` with a full download, and every sync after that was ordinary. Unit tests cover the server protocol (epoch mismatch, rollback, pagination during a reset, reviews carried by a reset request, the upgrade from version 2) and the phone side (cache replacement, history re-opened, an interrupted reset resuming, a cursor moving backwards not being mistaken for a stall).

## Worth fixing soon

### 6. Request size is only enforced after the whole body has arrived (confirmed) — FIXED
The 30 MB cap was checked in the handler, but FastAPI had already received and parsed the full multipart body by then: in an experiment a 240 MB upload took 0.94 s to be rejected with 413, against 0.05 s for 1 MB, so the time scaled with the body. `/sync` and the other JSON endpoints had no body limit either. I wrote here that only the token holder could send these. **That was wrong**: FastAPI reads a request's body before it runs the token check, so an anonymous client's upload was received and parsed too, and only then answered 401 (found in the security review below).
**Fixed:** a small ASGI middleware (`app/core/bodylimit.py`) answers `413` as soon as a request announces a body over the limit, before reading any of it, and cuts off a body that arrives without a length once it passes the limit. `POST /documents` gets `SNAPNOTES_MAX_UPLOAD_MB` plus 1 MB for the multipart framing; everything else gets `SNAPNOTES_MAX_BODY_KB` (default 2048, and a maximum-size sync batch of 500 reviews is far below it). The handler's own total-size check stays. A refused request still carries the CORS headers, so the browser preview shows the real error.
**Verified** with 11 new tests (the middleware driven by hand: inside the limit, declared too large, chunked, a length header that understates the body, only POST uploads get the larger limit, non-HTTP traffic; and through the real app: no upload folder or job is created for a refused upload). Also against a real `uvicorn` process over a raw TCP connection: announcing a 500 MB upload and sending nothing got `413` in 0.00 s (previously the server would have waited for the body); announcing 5 MB to `/sync` got `413` at once; a 40 MB chunked upload with no length header was cut off after about 32 MB had been sent; an ordinary request on a new connection afterwards got `200`; the server log showed no errors.

### 7. The access token has no minimum strength — FIXED
The server only refused an empty token. `SNAPNOTES_TOKEN=dev-token` was accepted in production, and the token is the only thing between the internet and your library and your Claude bill.
**Fixed:** the server refuses to start with a token shorter than 24 characters, and the error shows the command that makes a good one (`python -c "import secrets; print(secrets.token_urlsafe(32))"`). Demo mode is exempt (it spends nothing and the canned data is not private), and `SNAPNOTES_ALLOW_WEAK_TOKEN=1` switches the check off deliberately. While there: whitespace around a token from the environment is now stripped, since a trailing newline pasted into a secret is a classic cause of "the right token is rejected". Covered by tests for the boundary (23 refused, 24 accepted), a generated token, both exemptions and the startup refusal.

### 8. The rate limiter never forgets clients (confirmed) — FIXED
`SlidingWindowLimiter.prune()` existed but was never called, so the per-client table grew with every distinct client key. On Fly the key is Fly's `fly-client-ip` header, which Fly sets, but anywhere else the key was spoofable.
**Fixed:** the table holds at most 10,000 clients (the least recently seen is forgotten first) and sweeps expired ones every 1,024 calls. The header that names the client is now a setting (`SNAPNOTES_CLIENT_IP_HEADER`, default `fly-client-ip`); set it to an empty value anywhere your own proxy does not set it, and the connection's real address is used, so a caller cannot choose their own identity. The trade-off: under a flood of invented clients a real client's count can be forgotten, which makes the limit more lenient for them, never stricter. Tests: 50,000 made-up clients stay within the cap, eviction order, the sweep with no one asking, and the header trusted versus ignored.

### 9. Production runs a different Python than the tests (confirmed) — FIXED
The image used `python:3.12-slim`; every test and experiment here ran on Python 3.14 (the only interpreter installed).
**Fixed:** the image is pinned to the version that was tested (`ARG PYTHON_VERSION=3.14` in the `Dockerfile`, used by both stages), and there is an opt-in test stage: `docker build --target test .` installs the dev lock file and runs the whole suite inside the image's own environment (a normal `fly deploy` build skips it). One test that checks `fly.toml` against `DEPLOY.md` skips itself there, because neither file is in the Docker build context.
**Not verified:** the image was never built (no Docker here). What I did run is the same sequence of steps in a clean virtualenv on Python 3.14.5, with the build context mimicked: locked install, the app, `pip check`, the dev lock, and the suite (142 passed, 1 skipped, as expected). The base image will carry whatever 3.14 patch release is current when you build.

### 10. Dependencies are not pinned — FIXED
`pyproject.toml` uses lower bounds only, so two builds a month apart can differ.
**Fixed:** `backend/requirements.lock` (runtime) and `backend/requirements-dev.lock` (plus the test tools) pin every package, including indirect ones, to an exact version with a checksum for every file (generated with `uv pip compile --universal --generate-hashes` for Python 3.14). The `Dockerfile` installs the runtime file with `pip install --require-hashes --no-deps`, then the app itself, so a package that changed on the index is refused rather than installed. Regeneration steps are in `backend/README.md`; `DEPLOY.md` says when to do it.
**Verified:** a clean install from each lock file succeeded with `pip check` clean; the full suite passes in the locked dev environment; an environment built from the runtime file alone (no pytest, no httpx) boots the app and serves `/health`, `401` without a token and `200` with one; pip refuses a wrong hash and an unpinned line in that mode; all 33 pinned packages that apply on Linux have Python 3.14 wheels for both x86-64 and ARM (the 34th is an emscripten-only marker) (so the image build needs no compiler); and `pip-audit` on the locked set reports no known vulnerabilities. One thing is not pinned: `setuptools`, the build tool for the app's own package, which exists only during the image build.

## Lower priority

- **Rejected reviews vanish quietly.** The server lists reviews it cannot store (`bad_time`, `unknown_card`, ...) in `rejected`, but the phone marks them uploaded and never shows anything. A phone whose clock is more than a day ahead would lose its history from the server without any message.
- **Abandoned uploads are never cleaned up.** A document left at "awaiting approval", or a failed job, keeps its original files on the volume until you discard it. A year of forgotten uploads could fill a 1 GB volume. A time limit (for example 7 days) would fix it.
- **Plain `http://` to a public host sends the token in clear text.** Installed builds refuse `http://`; in Expo Go or a dev build, typing `http://myapp.fly.dev` would send the token before Fly redirects to HTTPS. Warn when the host is not a private or local address.
- ~~**No `.gitignore` at the project root.**~~ **Fixed** before the first commit: the root `.gitignore` covers env files, key and certificate files, databases, debug dumps and `.claude/` (the preview launcher, which holds the demo token and local paths). The Expo template's nested `mobile/.git` repository (one template commit, no remote) was moved out of the project so one repository covers both folders.
- **Store release.** Sending notes to a third party (Anthropic) needs a privacy policy and the store privacy declarations; replace the placeholder `com.snapnotes.app` identifiers in `mobile/app.json` before building.

## Not a problem (checked)

- `npm audit` reports 19 "high" advisories, all in Expo's build tooling (Metro, `braces`, `node-forge` via code signing). None ships in the app, and the suggested fixes would downgrade Expo to an ancient version. **Do not run `npm audit fix --force`.**
- `pip-audit`: no known vulnerabilities in the backend's dependencies.
- Every SQL statement is parameterised; the f-strings only build table/column names from fixed lists or `?` placeholders.
- Token comparison is constant-time; the token is never logged, never put in a URL, and stored in the OS keychain on the phone.
- Uploaded filenames are replaced by generated names, files are written under a server-generated folder, and `DELETE /documents/{id}` only removes a folder after the database confirms the id exists, so path traversal is not possible.
- CORS and the interactive API docs are off by default and off in the image; the container runs as a non-root user; Fly forces HTTPS.
- Card text in Anki exports is HTML-escaped (apart from finding 2), the CSV export neutralises spreadsheet formulas, and the `Content-Disposition` filename is sanitised and encoded.
- The server never fetches URLs on a user's behalf (web search runs at Anthropic), so there is no server-side request forgery surface.
- Notes, web content and filenames are treated as data in prompts, with delimiter escaping.


## Security review (October 2026)

Two read-only reviews (server; app and repository) plus black-box probes of a throwaway server. Nothing secret or personal was found in the repository or its history. What was found and fixed:

1. **A production build could contain the dev token (high).** `start.ps1` hands the dev server and token to Expo as `EXPO_PUBLIC_` variables, and Expo copies every such variable it sees into the JavaScript bundle at build time. The `__DEV__` test was only a default argument inside a function, so the strings stayed in a release bundle (confirmed by building one with a made-up token and finding it). **Fixed:** the variables are now named only inside `if (__DEV__)` at the call site, which a release build replaces with `false` (the same build now contains neither the token nor the address), and `start.ps1` removes them from the terminal once its app window has its own copy.
2. **The body was read before the token was checked (medium).** An anonymous 20 MB upload was received in full before the 401. **Fixed:** `app/core/authgate.py`, an ASGI layer placed after the rate limiter (so wrong guesses still count) and before the body limit, answers 401 without reading any of the body. `require_auth` stays on every route as a second check.
3. **A small DOCX or PPTX could exhaust memory and CPU (medium, needs the token).** A 779 KB file that unpacks to about 196 MB kept the server busy for over five minutes and used about 1.3 GB. **Fixed:** before anything parses an Office file its zip directory is read, and a file whose XML unpacks to more than 25 MB (200 MB in all, or more than 20,000 parts) is refused with a clear message. The same file is now refused in 0.3 s.
4. **Originals could pile up and the hourly job cap could be dodged (medium).** Failed jobs and jobs waiting for approval kept their originals for ever, and deleting a job removed the row the cap counted. **Fixed:** uploads from jobs nothing is running are deleted after `SNAPNOTES_UPLOAD_TTL_DAYS` (default 14; at start-up and at most every six hours), the cap also counts uploads from a memory that deleting does not reset, and an upload is refused with `507` when the disk has less than twice the upload limit free.
5. **The dev servers listened on the whole Wi-Fi (medium).** `run-dev.ps1` now listens on this computer only (the emulator reaches it as 10.0.2.2) unless `SNAPNOTES_DEV_URL` is set in `backend/.env` for a real phone.
6. **Plain http was not enforced (medium).** The app now assumes https for an address typed without a scheme unless it is on your own network, and refuses on every request to send the token over http to an address that is on the internet (in an installed app, any http). An address saved earlier or handed over by a script gets no pass.

Reported and left for later (low): the Anki deck description is not escaped; `/docs` is on by default when run locally (off in the Docker image); the rate limiter trusts the client-address header unless behind Fly; cost ceilings are checked between stages, not within one; ids from deep links are not URL-encoded; Android backup is allowed; sync responses are not validated; `Read-Host` shows the Gemini key; some `.gitignore` patterns for keystores and APKs are missing; four dependencies are unused; `npm audit` lists 5 high in build tooling only (do not run its `--force` fix, which would install a much older Expo).
